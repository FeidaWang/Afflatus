# 从 Vibe Coding 到个人 FDE：24 周把 AI 变成可维护的生活基础设施

> 一条面向有 AI 编程经验、具备初中级 IT 基础、没有计算机相关本科学位的实践路线。学习目标不是生成更多代码，而是把真实问题变成可以理解、验证、部署、维护和持续使用的工具。

**资料核对基线：2026 年 9 月 27 日｜版本：公开分享版 1.0｜形式：自学课程与项目实验，不是大学学位、职业认证或就业承诺。**

本文的周数、阅读时间、实验规模和过关标准均为课程设计建议；研究结果与平台规则在对应位置给出原始来源。链接到课程不等于获得其全部实验、证书或付费内容的访问权。公开资料的核对范围见文末资源表，实施时仍需检查当前版本。

## 导读：为什么不是另一份“AI 课程大全”

很多人已经能够用自然语言做出网页、脚本甚至完整应用，却仍然面对同一组问题：代码出错后只能让模型重写；工具在演示中很好用，进入生活却增加维护；资料收藏了很多，但下一次遇到同类问题仍然不知道如何判断；模型不断更新，项目却也随之不断推倒重来。

这里要补的不是更多提示词，而是一条完整的能力链：

**发现一个重复问题 → 选择最简单的解决办法 → 理解核心实现 → 检查结果 → 在合适环境运行 → 接管故障 → 证明它值得保留。**

本文借鉴 FDE（Forward Deployed Engineer，前线部署工程师）式的端到端工作方式，但把第一个使用者设为自己。“个人 FDE”是本课程对学习路径的命名，不是行业统一认证名称。课程中的 RSI 按 Recursive Self-Improvement 理解，主线仅指对提示、工具、工作流和代码进行受控改进，不声称实现基础模型权重自训练或无限智能增长。

三个问题贯穿全程：**我能解释吗？我能验证和恢复吗？它真的改变了我的日常吗？**

## 一、怎样使用这份路线

### 1. 适合谁，以及不适合怎样使用

适合已经尝试过 AI 编程、会使用电脑和常见 IT 工具，但软件基础并不系统的人。完全初学者可以先做下文桥接，再进入主线；有经验的工程师可以直接做诊断与验收，补真正的缺口。

不要把它当成必须连续二十四周不间断完成的挑战，也不要把大学公开课全部堆成前置条件。每周只有一个主问题、一个可见交付和一项独立练习。完成标准是能力，而不是日历翻页。这里没有“必须先花钱购买某一款模型”的入学门槛。

已有项目的人优先改进自己的低风险项目；没有项目的人沿用本文三个通用案例。不要同时积极开发三个系统，每次只推进当前主项目，其余只做实际使用与必要维护。

### 2. 时间预算：每周十小时核心，两小时机动

| 环节 | 核心预算 | 应留下什么 |
|---|---:|---|
| 选读官方课程与文档 | 2 小时 | 当前问题的理解与一两个疑问，不是所有视频观看记录 |
| 构建和验证 | 5 小时 | 一个有用的最小改动与实际检查结果 |
| 不用代码生成器的小练习 | 1 小时 | 自己解释、修改或修复一个问题 |
| 在真实低风险任务中使用 | 1 小时 | 使用情况与摩擦，不只是演示截图 |
| 复盘、维护与资料更新 | 1 小时 | 继续、简化、暂停或删除的决定 |

每周可再留两小时补基础。按每周 10–12 小时估算，24 周的计划投入为 240–288 小时；每周只有 6 小时，可以把同样工作量摊到约 40–48 周，基础差距和任务复杂度仍可能继续延长。

每周资源表的分钟数是**建议阅读预算**，不是整门课的官方时长。表中“选读”“复习”“补基础”不是额外全修要求；超出两小时后，优先读当前任务卡住的内容，剩余放进机动时间。读完不等于掌握，没读完也不必阻止一个已被理解的小交付。

### 3. 先做诊断，不先买一整套课程

用 60–90 分钟完成以下检查。可以查官方文档，但先保留自己的首次答案，不让 AI 代答。

| 检查点 | 合格表现 | 暂时不会时补什么 |
|---|---|---|
| 小函数与数据 | 能解释输入输出，预测一组新数据的结果 | [R12 · CS50P Week 0：Functions, Variables](https://cs50.harvard.edu/python/weeks/0/) 或 [R27 · MDN：JavaScript Guide](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide) 的函数、变量、集合 |
| 错误与测试 | 能读错误位置，写一个反例与期望结果 | [R03 · MIT Missing Semester：Debugging and Profiling](https://missing.csail.mit.edu/2026/debugging-profiling/)、[R13 · CS50P Week 5：Unit Tests](https://cs50.harvard.edu/python/weeks/5/) |
| 文件与运行环境 | 能说明当前目录、读写位置、怎样启动 | [R02 · MIT Missing Semester：Course Overview and the Shell](https://missing.csail.mit.edu/2026/course-shell/)、[R14 · CS50P Week 6：File I/O](https://cs50.harvard.edu/python/weeks/6/) |
| Git 与安全修改 | 能看差异、保存可用版本、撤销一个改动 | [R04 · MIT Missing Semester：Version Control (Git)](https://missing.csail.mit.edu/2026/version-control/)、[R31 · Pro Git：在线书籍](https://git-scm.com/book/en/v2) |
| Web 数据流 | 能区分浏览器、服务器与外部 API | [R26 · MDN：Core learning modules](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core)、[R32 · MDN：Overview of HTTP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview) |
| 数据与秘密 | 能区分零与未知，知道凭据不该放前端或公开仓库 | [R17 · Harvard CS50 SQL](https://cs50.harvard.edu/sql/)、[R59 · OWASP：Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html) |

大量缺项时，加一段约 4–8 周的桥接：第一段练函数、分支、循环和数据；第二段练文件、错误与测试；第三段练 Git、环境与 Web 数据流；第四段用一个本地工具串起来。时间只是安排，仍不会时继续补。算法、内存和数据结构可以从 [R16 · Harvard CS50x 2026](https://cs50.harvard.edu/x/) 按缺口选学，不需要先把全部本科课程修完。

### 4. 一条主技术栈，不同时学五个框架

默认主线选择 **JavaScript / TypeScript → React → Node → SQL → Git**。已有稳定技术栈的人可以保留，不必为了这篇文章重写。Python 只用于补基础、阅读研究和小实验；前六周不要同时建设两套完整后端。

[R28 · TypeScript Handbook：Introduction](https://www.typescriptlang.org/docs/handbook/intro.html)、[R29 · React：Quick Start](https://react.dev/learn) 与 [R30 · Node.js：Learn](https://nodejs.org/learn) 是语言和运行时查阅入口。[R21 · Full Stack Open：About the course](https://fullstackopen.com/en/about/) 列出了 Full Stack Open 的先修期待，因此先补基本编程与 Web，再选其中相关部分。向量数据库、Kubernetes、微调、多 agent 集群和复杂消息系统都不是开工前置条件。

实现顺序保持克制：规则能解决就用规则；需要语言理解才引入模型；步骤固定就用工作流；只有需要受约束地选择行动时才增加 agent 自主性。简单优先的工程思路可参考 [R41 · Anthropic：Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)。

## 二、2026 年应吸收什么，又不应该追什么

MIT Missing Semester 已有 2026 课程，其中包含 Agentic Coding；它适合补齐终端、Git、调试与交付这类容易被跳过的能力。Stanford CS146S 当前主页为 Fall 2026，涉及 MCP、skills、规格与人机协作循环，但明确要求相当于 CS111/CS161 的编程经验；不能把它说成零基础课，也不能据课程介绍假定未来全部材料已经开放。资料见 [R01 · MIT Missing Semester：2026 课程目录](https://missing.csail.mit.edu/)、[R06 · MIT Missing Semester：Agentic Coding](https://missing.csail.mit.edu/2026/agentic-coding/)、[R09 · Stanford CS146S：The Modern Software Developer，Fall 2026](https://themodernsoftware.dev/)。

当前工程材料值得学习的，不仅是提示词，还包括执行环境、仓库信息、反馈与结果检查。本文从 [R47 · OpenAI：Harness engineering](https://openai.com/index/harness-engineering/)、[R42 · Anthropic：Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) 等原始文章中选取相关思路，再设计自己的练习；没有复制厂商内部成绩，也不保证同样收益能够在个人项目复现。

AI 辅助完成任务与学习者掌握技能是两个不同目标。一项受控编程学习研究提示，使用方式与理解形成有关，但它的样本、任务和实验条件有限，不能推广为“AI 一定损害学习”。本课程因此保留独立解释和新情景练习，而不是禁止使用 AI。研究来源见 [R45 · Anthropic：How AI assistance impacts the formation of coding skills](https://www.anthropic.com/research/AI-assistance-coding-skills)。

选课只保留少量主线：基础用 MIT、MDN 与 CS50 的对应章节；Web 交付用 Full Stack Open 与官方文档；agent 基础用 Hugging Face 加一个主 SDK；后期再选 Berkeley 2025 的进阶材料、GEPA 和 DGM。厂商培训在 [R38 · OpenAI Academy：Codex](https://openai.com/academy/codex/) 与 [R39 · Claude Academy：Claude Code in Action](https://academy.claude.com/courses/claude-code-in-action) 中选择自己实际使用的一条即可，不需要两套从头重复。

**“前沿”应表现为能及时核对变化、做小范围验证和删除过时机制，而不是永远重建技术栈。**

## 三、三个持续项目，以及它们的数据边界

| 项目 | 要解决的问题 | 第一版边界 | 主要训练阶段 |
|---|---|---|---|
| P1 本地周计划工具 | 重复录入、时间冲突与计划导出 | 本地处理，手动导出；时段与规则由用户配置，不写入私人云日历 | 第 1–8 周 |
| P2 知识行动工作台 | 资料难追溯、读完没有行动 | 少量公开来源，先只读，输出证据与行动卡 | 第 9–18 周 |
| P3 AI 任务与成本账本 | 模型选择凭印象、用量与返工不清楚 | 只记录授权可得的最小元数据，不收集完整私人对话 | 第 19–24 周 |

公开教程中的名字、数据和任务均为通用教学设计，不对应具体个人、雇主、客户或真实项目。不要把自己的真实记录直接替换进公开示例后再次发布。

推荐的架构由风险推动，而不是由框架流行度推动：

```text
P1：用户输入 → 本地规则与校验 → 预览 → 用户主动导出

P2：固定公开来源 → 只读检索 → 必要时调用模型
                         ↓
              证据校验 → 行动草稿 → 人工决定
                         ↓
                    最小运行记录

P3：授权可得的任务元数据 → 本地统计 → 改进提案
                                      ↓
                         隔离评测 → 人工批准或拒绝
```

这是一张课程架构示意，不代表已经部署的服务。所有跨网络边界都要重新判断数据、权限与费用；模型提出动作，不等于已经获得执行许可。

## 四、学习时怎样使用 coding agent

采用一个固定循环：**先自己预测 → 协作实现 → 解释数据流 → 独立小改动 → 新情景验证。**

不要让模型一次读完全部二十四周并开始连续执行。当前周只给目标、必要文件、输入输出、非目标和安全边界；让它先检查真实项目状态，再提出最小计划。每轮结束保留实际验证、未验证项和下一步，不要求它为每个细节制造长报告。

导师、开发者与复核者可以是同一个模型在不同阶段扮演的角色，也可以用两个工具分工。第二个模型的同意只是额外线索，不能替代代码执行、原文证据和人对外部结果的确认。独立练习期间，模型可提问但不提前显示完整答案。

下面的提示词可以作为每周提示的共同前提：

```text
你是我的工程导师和协作开发者。先确认本周目标与当前项目状态，
只处理一个小而完整的任务，不自动推进下一周。

我需要理解输入、处理、输出、失败、权限、费用和恢复方法。
先给最小规格与非目标，再实现最少改动，并实际执行相关检查。
结果分成：已交付、已验证、未验证、风险或限制、我的独立练习。

默认使用合成或公开数据，默认 mock、只读、手动触发。
未经明确授权，不联网发送私人数据、不启用付费调用、
不连接账号、不公开发布、不扩大权限、不删除或覆盖源数据。

不把配置文件或提示词中的限制说成已经落实的安全控制。
不编造测试结果、运行历史、用量或用户反馈。
遇到基础缺口先缩小任务、解释并出小练习，不用大规模重写掩盖它。
```

这段提示词只是沟通约定，不是安全边界本身。真正的文件、网络、预算和动作限制必须由系统权限与执行程序落实。外部课程的正式作业另外遵守其学术诚信要求，例如 [R15 · CS50P：Academic Honesty](https://cs50.harvard.edu/python/honesty/)；本文鼓励 AI 协作的自有项目不应成为规避课程规则的理由。

<a id="w01"></a>
## 第 01 周｜从生活摩擦出发：诊断基础，做出第一个本地工具

> **本周要回答：** 不是先问“我能做什么 agent”，而是问“我每周重复做的哪件小事，值得被可靠地减少一次？”

**进入本周前：** 能操作电脑、安装常用软件；不要求已经掌握某门语言。先确认自己有权在设备上安装开发工具。

### 学习内容与理解目标

本周先建立三个区别：文件是数据，程序是处理规则，运行环境决定规则在哪里执行。把输入、处理、输出画成三个方框，再补上错误和恢复路径。诊断应覆盖读懂小函数、查看数组或对象、解释 JSON、认识终端当前目录、理解浏览器与服务器、检查代码差异和识别秘密信息。不会的项目标成“待补”，不让 AI 代替你答完诊断。

第一个工具宜选择文本清单去重、学习任务时长汇总、公开书目整理等低风险功能。它可以只有一个脚本或一个离线页面。本周不接邮箱、不购买额外服务、不做账号系统；也不碰自动删除、批量改名等需要恢复能力的操作。

### 实战拆解

## 第 09 周｜从一次模型调用到最小 agent：先明确何时不需要自主性

> **本周要回答：** 这项任务需要语言判断，还是只需要一条清楚的程序规则？

**进入本周前：** 能读懂简单函数、HTTP 请求和结构化数据；不要求会训练神经网络。

### 学习内容与理解目标

先分清四层：确定性函数、一次模型调用、预定步骤的工作流、可选择下一步工具的 agent。本周只构造最小只读循环：收到问题、选择已授权工具、检查参数、读取合成材料、返回结果并停止。模型可以提出动作，但执行器决定动作是否被允许。

补足 LLM 的工程常识：输入输出受长度和预算约束，生成结果可能不稳定，结构正确不等于事实正确。理解工具调用是结构化请求，不是模型真的拥有任意系统权限。先用固定 mock 输出理解流程，再选择一个官方 SDK；主线不同时实现多个框架。概念阅读见 [R41 · Anthropic：Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) 与 [R37 · Hugging Face：Introduction to Agents，Unit 1](https://huggingface.co/learn/agents-course/en/unit1/introduction)。

### 学习链接与选读范围

| 级别 | 官方或原始资料 | 本周只读这些 | 阅读预算 |
|---|---|---|---:|
| 必读 | [R37 · Hugging Face：Introduction to Agents，Unit 1](https://huggingface.co/learn/agents-course/en/unit1/introduction) | Agent、LLM、tool 与 action/observation 循环相关材料。 | 45 分钟 |
| 必读 | [R41 · Anthropic：Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) | 工作流与 agent 的区别，以及优先简单方案。 | 30 分钟 |
| 实现选读 | [R48 · OpenAI Agents SDK for TypeScript](https://openai.github.io/openai-agents-js/) | 选一个最小 TypeScript agent 与工具定义示例，核对当前 API。 | 45 分钟 |

### 实战拆解

1. 选一个公开资料小任务，例如从三份合成学习记录中找待复习主题。先实现不用模型的基线，说明哪些步骤已经能靠程序准确完成。

2. 约定一个结构化结果，至少包括答案、证据标识、无法回答原因。用运行时 schema 检查，不接受为了通过校验而捏造必填字段。

3. 写 mock 模型：分别返回正常工具请求、未知工具、错误参数和停止信号。执行器只能访问允许的资料，工具输入必须再次校验。

4. 加入总步数、超时和重试边界；触发边界时返回明确的未完成状态。先确认 mock 会按边界停止，再决定是否进行少量真实调用。

5. 比较模型方案与确定性基线：在哪种语言任务上有额外价值，在哪种任务上只是更慢、更贵或更不可预测。保留不使用 agent 的决定。

### 交付与验收

| 本周交付 | 怎样确认真的完成 |
|---|---|
| 最小只读循环 | 正常路径可执行，未知工具与越界参数被执行器拒绝。 |
| 结构化结果 | 格式检查与证据检查分开；缺证据时允许不回答。 |
| 方案选择说明 | 指出 agent 比普通函数多解决了什么，或明确决定暂不采用。 |

**不用代码生成器的练习：** 不使用代码生成器，画出一次工具调用的消息与执行顺序；然后增加一个不被允许的工具名测试，确认不是靠模型自觉拒绝。

**隐私与安全检查：** 不开放 shell、任意文件读取、自由 URL 抓取和写入权限。预算、停止条件和工具许可必须在执行器实现，写进提示词只是辅助。此阶段使用公开或合成材料，不接真实账号。

**落到日常生活：** 让原型处理一个真实存在但低风险的信息查找需求，亲自打开证据核对。若传统搜索更省事，就让模型只承担整理而不是整个流程。

**过关或补课判断：** 能解释工具循环、拒绝未知工具、区分格式与事实后进入评测阶段。无法确定调用成本时继续使用 mock。

### 本周可复制的协作提示

```text
请先比较确定性函数、单次调用和只读 agent 三种方案。用 mock 构造工具循环，并在执行器落实参数校验、步数上限和停止状态。未经我明确授权，不发起付费调用或连接账号。
```


<a id="w10"></a>
## 第 10 周｜为 agent 建立评测：让“完成了”有外部证据

> **本周要回答：** 模型说任务成功，文件、数据库或用户实际得到的结果真的成功了吗？

**进入本周前：** 已有最小只读 agent；能复现一次工具执行和记录最后状态。

### 学习内容与理解目标

评测不是准备几个好看问题截图，而是明确任务、预期结果、允许的证据、失败类型与成本。本周把结果检查分成机器能判断的条件、需要人工判断的质量，以及允许用模型辅助但必须复核的部分。格式合法、引用真实、任务完成和表达流畅是不同维度。

评测集既要有正常输入，也要包括缺证据、错误版本、工具失败和必须拒绝的情况。初期十几条只是冒烟检查，不足以说明总体可靠性。对随机行为可重复运行，但要记录尝试次数，不能只保留最好的一次。工程思路参考 [R42 · Anthropic：Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)；本课程的具体题目与门槛由自己的任务决定。

### 学习链接与选读范围

| 级别 | 官方或原始资料 | 本周只读这些 | 阅读预算 |
|---|---|---|---:|
| 必读 | [R42 · Anthropic：Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) | 结果、执行轨迹、评分方式与回归的关系。 | 55 分钟 |
| 复习 | [R13 · CS50P Week 5：Unit Tests](https://cs50.harvard.edu/python/weeks/5/) | 把明确结果写成独立可运行的检查。 | 25 分钟 |
| 选读 | [R36 · Hugging Face：Agents Course Introduction](https://huggingface.co/learn/agents-course/en/unit0/introduction) | 课程中评估与任务实践的入口；不以证书替代本项目验证。 | 30 分钟 |

### 实战拆解

1. 先写任务成功定义，再构造约 10–20 条覆盖不同情形的合成案例。为每条记录输入、期望行为、证据位置、拒绝条件和严重程度；数量是练习规模，不是可靠性认证。

2. 实现客观检查：结构有效、引用标识存在、没有调用禁止工具、需要停止时确实停止。对“答案是否受到证据支持”保留人工核验项。

3. 分别评测普通函数基线和 agent 原型。记录成功、失败、无法判断和超时，未测结果不能填成成功；保留完整分母。

4. 挑两条失败做最小复现，并修复一个共因。使用相同案例回归，但不同时修改题目和成功标准来美化成绩。

5. 开始划分开发集与独立保留集：用于最终判断的答案不提供给候选生成者。真正隔离需要独立目录权限或执行身份，不是只写一句“不要看”。

### 交付与验收

| 本周交付 | 怎样确认真的完成 |
|---|---|
| 初版评测集 | 题目、期望、来源与失败类型明确；包含拒绝和坏输入。 |
| 可检查报告 | 记录所有尝试及真实最终状态，不仅是模型文本。 |
| 一次错误分析 | 能说明失败来自工具、资料、推理还是验证方式。 |

**不用代码生成器的练习：** 自己设计一道能骗过当前“看起来正确”检查的题，再改进检查而不泄露答案给被测 agent。

**隐私与安全检查：** 评测原文、轨迹和保留集也可能包含秘密。公开只发布经过检查的合成案例与方法；完整工具参数和输出按最小必要原则记录。不要把真实隐私样本上传到第三方评分服务。

**落到日常生活：** 为最常见的一项个人任务固定几条复核问题。以后更换模型或提示词时先跑这些问题，而不是凭一次顺畅对话判断进步。

**过关或补课判断：** 能指出一个“格式通过但实际失败”的例子，能稳定复现关键问题，才继续增加工具能力。

### 本周可复制的协作提示

```text
请先写外部可核验的成功标准，再设计少量覆盖边界的评测。记录所有失败、超时和未知，不允许根据模型自述直接判成功。把开发题与最终保留题隔开，并让我独立补一条反例。
```


<a id="w11"></a>
## 第 11 周｜上下文、skills 与 MCP：把能力接进来，也把权限挡住

> **本周要回答：** 给 agent 更多上下文和工具，会带来更可靠的结果，还是更大的泄露与误操作空间？

**进入本周前：** 会运行评测，能解释工具执行器和模型建议的区别。

### 学习内容与理解目标

本周理解三类内容：长期有效的项目约束、当前任务状态、外部不可信资料。不要把它们混成无限增长的聊天历史。交接只保留目标、已验证结果、下一步、阻碍与必要文件位置；不要复制全部日志和私人对话。

Skills 可用于按需加载某类任务步骤，MCP 用于连接工具与资源；二者都不是自动获得信任的凭证。工具描述、仓库文档和网页都可能含误导指令。这里先做只读集成演练，学习参数、权限、身份、返回值和错误边界；具体安全要求看 [R57 · MCP：Security Best Practices，2026-07-28 版](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)。若某工具不支持某功能，就保留手动流程，不伪造自动续聊或删除能力。

| 必读 | [R43 · Anthropic：Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) | 选择上下文、压缩与检索的取舍；只采用当前确有需要的方法。 | 35 分钟 |
| 必读 | [R57 · MCP：Security Best Practices，2026-07-28 版](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices) | 授权边界、令牌与连接器相关风险，按版本核对。 | 45 分钟 |
| 必读选段 | [R58 · OWASP：LLM Prompt Injection Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html) | 间接提示注入、工具限制与分层防护。 | 40 分钟 |

### 实战拆解

1. 将当前项目说明缩成一页，只放运行方法、边界、测试与完成标准。另写一张交接卡，下一轮只读相关模块，不把全部资料默认塞入上下文。

2. 把一个反复执行的低风险流程写成可复用 skill：触发条件、输入、步骤、验证、停止条件。不要把它升级成能自行安装插件或扩大权限的总控。

3. 为一个只读工具列权限表：访问什么资源、允许哪些方法、参数范围、返回字段和超时。用 mock MCP 或已核对的只读服务练习，不接真实私人内容。

4. 在合成资料中放入一段无害注入示例，例如要求忽略任务并输出测试标记。评测系统是否仍把它当资料，而不是执行指令；重点检查执行器拒绝越权。

5. 比较完整历史与短交接在同一任务上的结果。记录丢失了什么重要信息；只有确有收益才保留更复杂的上下文机制。

### 交付与验收

| 本周交付 | 怎样确认真的完成 |
|---|---|
| 上下文与交接卡 | 不含完整私人日志，能让新会话接上一个具体任务。 |
| 工具权限表 | 允许和禁止范围明确，并有一次实际拒绝测试。 |
| 注入演练记录 | 记录输入与实际执行，不以“模型口头拒绝”替代权限验证。 |

**不用代码生成器的练习：** 自己给工具增加一条资源范围检查，并用一个越界参数测试；不能仅修改系统提示词。

**隐私与安全检查：** 禁止令牌透传、共享账号凭据和不明 MCP 服务。只读并不等于无风险：读取的数据仍可能被外传。没有必要不开放出站网络，敏感内容不进入工具返回和追踪日志。不要因教程出现高自主模式就关闭主机权限提示。

**落到日常生活：** 把一次经常中断的学习或开发任务改用短交接继续，亲自验证它是否比重读整个对话更轻松。真正的目标是恢复任务，不是让上下文监控本身成为负担。

**过关或补课判断：** 新会话能恢复任务，越权请求被实际拒绝，且不再默认信任外部文本，才开始知识工作台。

## 第 12 周｜知识工作台第一步：从来源到可追溯的证据

> **本周要回答：** 你收到的是有出处的结论，还是看起来流畅、却无法回到原文的二手解释？

**进入本周前：** 能处理结构化数据、运行只读 agent，了解外部资料与指令的信任边界。

### 学习内容与理解目标

开始项目 P2——知识行动工作台。先建立很小的公开来源库，每条来源包含标题、URL、作者或机构、发布日期或版本、读取日期、主题与证据位置。发布时间和读取时间必须分开；不知道发布日期就标未知，不猜。

检索先采用文件标签、关键词或 SQLite 全文搜索，再考虑嵌入和向量检索。对中文材料，分词与混合语言查询需要实测，不能只因为用了全文搜索就宣称召回好。回答应分成原文事实、自己的推断与尚待验证的问题；找到相关文章不等于文章支持生成的结论。

| 复习 | [R43 · Anthropic：Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) | 按问题挑选相关上下文，不无限抓取全部材料。 | 30 分钟 |
| 必读选段 | [R62 · OWASP：Server-Side Request Forgery Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html) | 固定来源与网络访问边界；理解为什么任意 URL 抓取有风险。 | 40 分钟 |

### 实战拆解

1. 选择 5–10 份真正与当前问题有关的公开官方材料，手工录入来源信息。优先保存自己的摘要、必要定位与链接；不要默认镜像整套课程、付费文章或受限制资料。

2. 建立一个简单检索接口，先测试是否找得到你已知的证据。记录关键词未命中的情况，再决定是否需要改进切分或检索方式。

3. 为一个问题生成证据卡：主张、来源位置、适用条件、反例或局限。允许输出“资料不足”，不为了填满模板强行得出结论。

4. 手工核查每条引用：链接存在只是第一步，还要看原文是否支持具体句子、版本是否适用。遇到来源冲突，把冲突写出来，而不是自动选更符合预期的一方。

| 最小来源库 | 版本、读取日期与证据位置可追溯；未知字段如实标注。 |
| 一份有依据的答案 | 事实、推断和不确定性分开，重要主张能回到原文。 |
| 检索失败记录 | 至少一个找不到或来源不足的案例，不伪造完整覆盖。 |

**不用代码生成器的练习：** 选一条生成结论，不看模型解释，独立找到支持或反驳它的原文，并写明适用条件。

**隐私与安全检查：** 抓取器不能访问本机、内网或云元数据地址，也不能只在初始 URL 上检查一次而忽略重定向后的目标。没有完整防护时使用人工选定的公开文档。外部内容按不可信文本处理，不直接渲染活动 HTML。

**落到日常生活：** 下一次学习新技术时，只为一个具体问题建立证据卡，而不是把整篇文章收藏后遗忘。把“读过什么”转成“现在可以判断什么”。

**过关或补课判断：** 来源能追溯、无依据会停止、检索错误能被发现，才进入行动实验。更多文档和更长摘要不算过关。



<a id="w13"></a>
## 第 13 周｜把知识变成行动：提出预测，做一个能失败的小实验

> **本周要回答：** 这周学到的知识，究竟改变了哪一个决定、动作或工作步骤？

**进入本周前：** 已有可追溯的来源和证据卡，能够区分事实、推断与假设。

### 学习内容与理解目标

知识行动工作台的目标不是继续生成摘要，而是为知识设置出口。本周学习把一个主张转成可观察预测：在什么条件下，改变哪个变量，会让什么结果发生变化？同时写出反例、代价和停止条件。观察到改善不一定证明原因就是你的改动；先用最小对照减少自我说服。

选低风险技术问题即可，例如结构化输入是否减少返工、短交接是否缩短恢复任务时间、固定来源过滤是否减少旧版本引用。不要拿健康、投资、雇佣或其他高后果决策当课程实验。一次只改一个主要变量，失败也要保存。

### 学习链接与选读范围

| 级别 | 官方或原始资料 | 本周只读这些 | 阅读预算 |
|---|---|---|---:|
| 选读 | [R47 · OpenAI：Harness engineering](https://openai.com/index/harness-engineering/) | 从反馈与约束中找一个可迁移到个人工具的小假设。 | 35 分钟 |
| 必读复习 | [R42 · Anthropic：Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) | 把预期改善转成结果检查，而不是文字印象。 | 35 分钟 |
| 必读选段 | [R45 · Anthropic：How AI assistance impacts the formation of coding skills](https://www.anthropic.com/research/AI-assistance-coding-skills) | 理解学习结果与任务交付不同；注意研究适用范围。 | 35 分钟 |

### 实战拆解

1. 从上周证据卡选一个与你实际痛点有关的主张。先写自己的解释，再写“我预测……因为……；以下情况可能不成立”。不让模型先替你形成完整判断。

2. 设计一个 30–60 分钟可完成的实验：固定任务、基线和判定规则，做一个小变更。将准备、执行和复核都计入时间，不能只统计成功输出速度。

3. 运行基线与改动版，保留所有结果。如果模型有随机性，增加少量重复并记录差异，不在结果出来后只挑最好的例子。

4. 记录采用、拒绝或证据不足。需要采用时将变化落实为一个代码补丁、操作清单或默认设置；不要停留在笔记里写“以后注意”。

5. 为下次真实使用设置一个自然触发：在准备某类任务时打开检查卡，而不是无限追加推送提醒。计划之后用新例子复测。

### 交付与验收

| 本周交付 | 怎样确认真的完成 |
|---|---|
| 一张行动卡 | 包括来源、解释、预测、反例、实验、结果与实际改变。 |
| 可复现的小实验 | 基线、变更与检查条件写清，失败结果没有被删除。 |
| 一个行为或流程改动 | 已经落实，或有充分理由明确不采用。 |

**不用代码生成器的练习：** 自己写出实验可能出现的第二种解释，并设计一个更小的核查来排除它；不能只请另一模型“确认我的结论”。

**隐私与安全检查：** 实验只在隔离副本与合成数据上改变行为。对外发送、删除、付款或更改重要日程不是低风险实验；不能以“为了验证自动化”为理由跳过审批。

**落到日常生活：** 选一个本周会再次发生的真实任务，实际使用新规则。记录是否减少犹豫、检索或返工，或者发现原来的习惯已经足够好。

**过关或补课判断：** 能从一条知识走到一次可观察的操作改变，即使结论是拒绝，也可过关。只有更多摘要、不发生行动，先停止扩充来源库。

### 本周可复制的协作提示

```text
请把一条有来源的技术主张改成可检验假设，设计低风险小实验，固定基线与停止条件。只改变一个主要变量，记录失败和替代解释。结论允许采用、拒绝或证据不足，不追求强行证明改进。
```

## 第 14 周｜检验真正掌握：复测、迁移与知识库减负

> **本周要回答：** 离开原来的例子和模型答案，你还能把这个方法用到一个新问题上吗？

**进入本周前：** 已经完成一张知识行动卡，并在真实低风险任务中尝试过。

### 学习内容与理解目标

学习效果不应只用“我看懂解释了”来衡量。本周安排闭卷解释、独立修复和新场景迁移：同一原理换一个例子，能不能重新识别输入、边界、失败与验证？AI 可以做提问者、出题者和反馈者，但不要在你回答前显示完整答案。

第 7 天和第 21 天复测是本课程建议的可执行节奏，不是对所有人的最佳记忆间隔。本周可以检查前几周知识，并为本周内容安排之后的复测。知识库也需要删除：重复、无来源、过期且没有历史价值的卡片不应永久堆积。

### 学习链接与选读范围

| 级别 | 官方或原始资料 | 本周只读这些 | 阅读预算 |
|---|---|---|---:|
| 必读复习 | [R45 · Anthropic：How AI assistance impacts the formation of coding skills](https://www.anthropic.com/research/AI-assistance-coding-skills) | 区分完成编程任务与形成独立理解，谨慎外推研究。 | 30 分钟 |
| 按需复习 | [R27 · MDN：JavaScript Guide](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide) | 根据暴露的薄弱项返回函数、异步或错误处理章节。 | 45 分钟 |
| 补基础 | [R16 · Harvard CS50x 2026](https://cs50.harvard.edu/x/) | 算法或数据结构相关材料；只补当前解释不清的概念。 | 45 分钟 |

### 实战拆解

1. 从前三周知识中选三个问题，先不用生成器回答：解释概念、找出一个反例、给出一个应用。记录卡住的位置，不把查到的答案算作首次掌握。

2. 选择一个新场景迁移。例如把日历中的重复处理思想用到资料导入，或把 API 的错误状态用到文件处理；先说明相同点与不同点。

3. 独立完成一个小变更，再让模型只做审查和追问。若它直接重写了全部答案，回到一个更小的问题继续练习。

4. 审查知识卡：保留实际用过、仍有依据和能引出下一步的内容；合并重复卡，对旧版本标记适用范围，删除没有用途的自动摘要。

5. 为少量重要知识设后续复测，不为每篇文章建立复杂打卡系统。学习工具本身的维护时间也进入周报。

### 交付与验收

| 本周交付 | 怎样确认真的完成 |
|---|---|
| 一份独立复测 | 记录首次回答与之后修正，清楚区分能做和只会查。 |
| 一个迁移应用 | 在新情景中成功使用原理，并解释边界变化。 |
| 知识库清理记录 | 删除或合并的理由明确，不以收藏量当成进步。 |

**不用代码生成器的练习：** 不调用代码生成器，修复一个你之前没有见过的小问题；允许查官方文档，最后讲清楚为什么修复有效。

**隐私与安全检查：** 出题时不使用他人的私人资料，不把正式大学作业答案交给受限制的外部 AI 生成后提交。自己的练习项目与课程评估分轨；相关要求见 [R15 · CS50P：Academic Honesty](https://cs50.harvard.edu/python/honesty/)。

**落到日常生活：** 观察学习是否让你少查一次重复问题、少做一次返工或更快识别一个风险。把这些变化记下来，允许结论是需要继续补基础。

**过关或补课判断：** 至少一次独立迁移成立后再扩大部署复杂度。若连现有工具都解释不了，应把第 15 周顺延，而不是按日历强行毕业。

### 本周可复制的协作提示

```text
请做提问者而非答案生成器，围绕我的三个知识点出新情景问题。先等我回答，再反馈缺口。最后帮助我合并无用笔记，并安排少量复测，不建立庞大的学习管理系统。
```

## 第 15 周｜部署只读运行时：明确运行位置、认证和每一笔费用

> **本周要回答：** 电脑合上后任务还会运行吗？由哪个账号付费？谁能打开结果？

**进入本周前：** P2 能手动工作，有基本评测与数据边界；理解浏览器和服务器，能恢复代码版本。

### 学习内容与理解目标

部署的是受控运行环境，不是把聊天窗口搬到网页。先区分开发 agent、应用运行 agent 与评测工具：它们可以使用不同模型、账号范围和费用预算。把运行方式分成两个可选路径：本地手动运行的个人工具，或带认证的只读托管服务；两者都是合格学习成果，不要求购买云服务。

本周先不自动调度。定义触发方式、运行身份、存储位置、谁能访问、如何停止，以及订阅、API、托管三笔费用分别如何计量。订阅支持哪些官方自动化由当时文档决定，不应假定任意自建应用都能免费调用模型；计费核对入口见 [R53 · OpenAI：ChatGPT 与 API 的计费管理](https://help.openai.com/en/articles/9039756-managing-billing-for-chatgpt-and-the-api-platform) 与 [R54 · Codex 使用与计费入口](https://developers.openai.com/codex/pricing/)。

### 学习链接与选读范围

| 级别 | 官方或原始资料 | 本周只读这些 | 阅读预算 |
|---|---|---|---:|
| 必读选段 | [R24 · Full Stack Open Part 3：Programming a server with NodeJS and Express](https://fullstackopen.com/en/part3/) | Node 服务、HTTP 接口和部署的相关部分。 | 40 分钟 |
| 必读 | [R60 · OWASP：Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) | 身份、角色和对象级访问检查，默认拒绝。 | 35 分钟 |
| 路径 B 选读 | [R71 · Render：Deploy a Node Express App](https://render.com/docs/deploy-node-express-app) | 部署一个 Node Express 服务的官方步骤；费用另外核对。 | 40 分钟 |

### 实战拆解

1. 画出运行图：用户手动触发，执行器读取固定公开来源，模型生成结果，结果存到受控位置。每个跨网络箭头写出字段、身份和费用归属。

2. 选择路径 A：在自己的设备运行 Node 进程并手动触发，说明睡眠、断网与关机的限制；或路径 B：按官方指南部署单个小服务，使用标准认证组件或托管访问控制，不自创密码协议。

3. 先部署不使用模型的健康检查与 mock 任务。通过另一未登录会话验证未授权请求被拒绝，错误响应不泄露配置；“别人不知道地址”不是验收标准。

4. 把密钥放到当前平台的秘密管理机制，运行前验证认证路径与预算。只有明确授权后才执行一两个真实只读任务，并记录实际费用或未知值。

5. 写下停止方式、凭据撤销方式、产物位置和清理方式。将真实配置与公开示例分开；文档里的默认模式保持 mock。

### 交付与验收

| 本周交付 | 怎样确认真的完成 |
|---|---|
| 可运行只读版本 | 运行位置、触发方式与睡眠/关机行为明确。 |
| 实际访问检查 | 未授权会话不能访问结果或触发任务；不能只检查页面有登录按钮。 |
| 三笔费用说明 | 订阅、API、托管分别列出来源；不知道费用时不自动运行。 |

**不用代码生成器的练习：** 自己追踪一次 mock 请求，从 HTTP 到执行器再到结果；故意移除一项配置，确认系统清楚拒绝而不是默认走真实服务。

**隐私与安全检查：** 生产秘密不进入前端构建、截图、评测附件或日志。消费订阅并不等于机构批准的数据处理环境，代码在本地也不等于模型推理留在本地。托管平台的日志、备份和子处理方应另行核查。

**落到日常生活：** 让自己从一个固定入口完成一次公开资料整理，不再手工打开开发工具才能运行；同时保留手动替代流程，避免服务故障阻断生活。

**过关或补课判断：** 能停止、能说明谁可访问、知道费用归属且未授权访问被实际拒绝，才增加调度。缺少其中一项就保留本地手动。

### 本周可复制的协作提示

```text
请先部署 mock 的只读运行时，明确本地或托管路径、认证、存储、停止和费用。默认不启用真实付费调用，不把密钥送入浏览器。未经确认不扩大可见范围，先验证未授权访问被拒绝。
```

## 第 16 周｜让运行能够恢复：持久状态、重试、幂等与备份

> **本周要回答：** 网络在中途断开、任务重复触发或进程突然重启，会不会造成重复动作和无法解释的状态？

**进入本周前：** 已有受控的手动只读运行时，能够定位一次请求和停止进程。

### 学习内容与理解目标

本周学习任务状态机：待运行、运行中、成功、失败、等待人工处理与取消。将任务状态存到适合当前部署方式的持久存储，而不是假定进程内变量或临时磁盘能跨重启保留。副作用发生前后都有不确定窗口，重试不等于重新从头盲做一遍。

幂等是重复请求不产生额外不希望的效果，不是简单“生成一个 ID”就自动得到恰好一次执行。对不确定是否已成功的外部操作，应先核对目标系统状态，必要时交给人工。持久状态选修见 [R49 · LangGraph JavaScript：Persistence](https://docs.langchain.com/oss/javascript/langgraph/persistence)；本地 SQLite 足够时无需为了学习引入复杂编排。

### 学习链接与选读范围

| 级别 | 官方或原始资料 | 本周只读这些 | 阅读预算 |
|---|---|---|---:|
| 选读 | [R49 · LangGraph JavaScript：Persistence](https://docs.langchain.com/oss/javascript/langgraph/persistence) | 状态保存、线程或运行标识、恢复的概念。 | 40 分钟 |
| 必读选段 | [R68 · Google SRE：Effective Troubleshooting](https://sre.google/sre-book/effective-troubleshooting/) | 用假设和证据定位中断与重试问题。 | 35 分钟 |
| 路径 B 选读 | [R72 · Render：Cron Jobs](https://render.com/docs/cronjobs) | 调度、运行限制和停止规则；不要假定支持持久磁盘。 | 35 分钟 |

### 实战拆解

1. 为每次任务创建不含私人信息的运行标识，持久保存状态和最小必要结果。明确相同触发、重复输入与真正的新任务如何区分。

2. 加入有限重试、退避、总超时与取消。只对适合重试的错误重试，格式错误或权限拒绝不应无限尝试；总预算覆盖所有重试。

3. 用 mock 演练：处理中断、工具超时、重复触发、返回后未保存状态。检查重复请求不会生成重复草稿；无法确定状态时进入待人工核查。

4. 确认托管文件系统的持久性与服务限制。使用定时任务时，状态要放在任务可安全访问的持久数据层；Render 的 cron 与磁盘能力分别核对 [R72 · Render：Cron Jobs](https://render.com/docs/cronjobs)、[R73 · Render：Persistent Disks](https://render.com/docs/disks)。

5. 制作一份合成数据备份，在新位置实际恢复，并核对记录数量与关键字段。确认恢复过程中不会自动重放外部动作。

### 交付与验收

| 本周交付 | 怎样确认真的完成 |
|---|---|
| 持久状态与去重 | 重启可找到运行状态，重复触发的行为有实际测试。 |
| 故障演练记录 | 涵盖超时、中断、重复与不确定完成状态。 |
| 可恢复备份 | 确实恢复过数据，说明恢复点、数据损失范围与限制。 |

**不用代码生成器的练习：** 自己制造一次同任务的并发触发，观察两次是否都获得执行权；解释为什么界面禁用按钮不能解决服务端并发问题。

**隐私与安全检查：** 备份和状态表同样需要权限与保留期限。日志避免记录完整模型上下文和凭据；只保留定位故障所需信息，参考 [R61 · OWASP：Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)。停止新任务并不自动取消已经排队或已发送到外部系统的操作，应明确剩余风险。

**落到日常生活：** 允许一个只读公开资料任务按明确周期运行，先低频且有限次数。没有变化时跳过推理，失败时给一个可操作提示，而不是连续发送无意义通知。

**过关或补课判断：** 能恢复状态、去重和停止，且知道不确定结果如何处理后再尝试带审批的写入。一次成功运行不足以过关。

### 本周可复制的协作提示

```text
请先为只读任务设计持久状态、去重、有限重试和取消。用 mock 演练中断与重复，不承诺恰好一次外部执行。确认临时与持久存储区别，并实际恢复一份合成备份。
```

## 第 17 周｜连接一个真实工作流：先生成草稿，再按范围审批

> **本周要回答：** 人点了一次“批准”，究竟批准了哪个对象、哪段内容、哪种动作和多长时间？

**进入本周前：** 只读系统能够认证、记录、停止和恢复；已核对准备接入服务的官方权限与账户规则。

### 学习内容与理解目标

本周只选择一个连接器，目标可以是生成一份个人提醒草稿或写入专用测试日历。先用模拟接口，再接自己拥有且有权使用的个人测试环境。无法或不愿连接账号时，生成本地草稿供人工导入是完全合格的替代路径。

审批不是一个泛化的“允许这个 agent 工作”。批准需要绑定目标、动作、具体内容、有效期和运行身份，内容或目标变化后重新批准。执行器在真正执行时再次检查授权与当前状态。高后果动作、付款、永久删除和工作系统变更不进入课程默认范围。

### 学习链接与选读范围

| 级别 | 官方或原始资料 | 本周只读这些 | 阅读预算 |
|---|---|---|---:|
| 必读复习 | [R57 · MCP：Security Best Practices，2026-07-28 版](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices) | 连接器认证、令牌使用、范围与信任边界。 | 40 分钟 |
| 必读复习 | [R60 · OWASP：Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) | 对象级检查与默认拒绝。 | 35 分钟 |
| 必读选段 | [R59 · OWASP：Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html) | 凭据存储、最小权限和撤销或轮换。 | 35 分钟 |

### 实战拆解

1. 写出连接器权限说明：为什么需要、访问哪个账号或测试容器、读取什么、可能写什么、如何撤销。先排除账号里的其他私人资源。

2. 实现草稿模式，只展示动作预览，不实际写入。预览中显示目标与内容的关键差异，不让模型自己把危险变化隐藏在长摘要里。

3. 将审批绑定到确定的 payload 与目标。改变内容、目标、权限范围或超出有效期后，原批准必须失效；实际执行前再次核查。

4. 先用 mock 测试未批准、批准过期、内容改变、权限撤销、重复执行。允许真实写入时，只对专用测试资源做一个可逆动作，并亲自验证外部状态。

5. 演练停止与撤销连接。清理测试产物，同时检查日志与队列中是否仍存在等待执行的动作。

### 交付与验收

| 本周交付 | 怎样确认真的完成 |
|---|---|
| 单连接器说明 | 访问目的、最小范围、凭据位置、撤销方法清楚。 |
| 有效审批队列 | 未批准与变化后的动作不能执行，批准不是无限通行证。 |
| 外部结果核验 | 使用 mock 或专用测试资源记录实际状态，说明是否真正接入。 |

**不用代码生成器的练习：** 自己尝试在批准后修改目标对象或内容，确认执行器拒绝，并解释审批为什么要绑定具体动作。

**隐私与安全检查：** 不能把个人订阅登录令牌当成可公开分发的应用密钥；不共享账号、不绕过授权、不将工作数据搬进未经批准的个人环境。外部服务的权限提示必须由本人理解后确认，模型不能替人扩大授权。

**落到日常生活：** 选一件日常重复的小事，把重复整理交给系统，把最后决定保留给自己。真正省时的草稿往往比高度自主但要反复检查的执行更有价值。

**过关或补课判断：** 能证明未批准不能执行、撤销有效、输出可核对才过关。没有这些条件就保持本地草稿路线，不视为学习失败。

### 本周可复制的协作提示

```text
请只设计一个最小权限连接器，先模拟、再草稿、最后才考虑专用测试资源的可逆动作。审批必须绑定目标与具体内容，变化后重新批准。不得连接工作账号、付款、删除或扩大权限。
```


<a id="w18"></a>
## 第 18 周｜从演示走向运维：运行观察、告警与事件处理

> **本周要回答：** 系统悄悄停止工作、持续返回旧资料，或不断重试时，你多久能发现，又能怎样恢复？

**进入本周前：** 系统具有状态、认证、停止和恢复能力；第 16–17 周已开始低频观察。

### 学习内容与理解目标

这一周把观察窗口延续到第 18 周，不要求在七天里伪造十四天数据。实际只运行了几天就如实报告。学习监测的是用户结果与资源状态：成功任务、失败与未知、排队、延迟、预算消耗和数据是否新鲜，而不仅是服务器还活着。

个人工具只需要少量可操作告警。每条告警应指向一个动作：重试一次、查看来源、暂停任务或撤销连接。没有人会采取行动的高频通知应删除。运维不是打造另一套大平台，而是让工具坏了之后仍可控。参考 [R67 · Google SRE：Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/) 和 [R69 · Google SRE：Postmortem Culture](https://sre.google/sre-book/postmortem-culture/)，只保留适合小系统的部分。

### 实战拆解

1. 整理第 16–18 周实际运行记录，明确观察起止与缺失。按任务结果统计，不把 HTTP 200 或模型回答完整当作工作完成。

2. 配置少量监测：连续失败、无新结果、预算接近限制和运行卡住。验证告警既能触发也能恢复；不要把每次成功都推送给自己。

3. 演练一个可控事件，例如来源不可访问、配置撤销或存储不可用。按手册先暂停，再定位、恢复和核查有没有重复动作。

4. 写一页事件说明：何时发现、影响哪些任务、发生了什么、证据是什么、如何恢复、下一次只改哪个关键点。避免把错误归咎于“模型不够聪明”。

5. 统计维护与复核时间，删掉无用日志、冗余通知和不稳定功能。若维护超过价值，降低频率或回到手动，不以保持全自动为荣。

| 真实运行报告 | 准确标明观察窗口、失败、未知和主动维护时间。 |
| 一页事件手册 | 停止、定位、恢复、核验与升级到人工的路径清楚。 |
| 一次演练证据 | 真实执行 mock 或测试环境故障，区分演练与生产事件。 |

**不用代码生成器的练习：** 不让 agent 接管，按手册独立完成一次停止和恢复；指出一条最容易误导人的日志或指标并修正。

**隐私与安全检查：** 遥测平台可能成为新的数据接收方。默认只记录运行标识、状态、用量与经过裁剪的错误，不自动上传完整提示、网页原文、个人输入或工具返回。任何新增日志也要有删除与访问策略。

**落到日常生活：** 连续观察这项服务是否真的成为习惯：发生任务时是否使用，失败时是否知道替代流程，是否因为通知太多而忽略它。把维护负担算进生活成本。

**过关或补课判断：** 本人能在不依赖模型的情况下停止与恢复，且报告不掩盖失败，才进入受控改进。


## 第 19 周｜建立可信经验：AI 任务账本、用量估计与不确定性

> **本周要回答：** 你推荐某个模型或强度，是因为它真的在同类任务上更合适，还是因为最近一次表现令人印象深刻？

**进入本周前：** 至少有少量真实运行记录，能区分任务、尝试、结果与人工复核；缺少数据也可以开始，但不能假装已经校准。

### 学习内容与理解目标

启动 P3——AI 任务与成本账本。每条记录只保留必要字段：任务类别、运行环境、真实模型或工具版本、可获得的推理配置、尝试次数、主动耗时、结果与用量来源。未知记为 null 或明确状态，不用零替代。原始提示与个人资料默认不收集。

比较模型时，任务难度、工具权限、上下文长度和重试策略都可能影响结果。中位数可描述典型情况，较差情形和失败比例也必须看；小样本只能支持局部观察。某个固定样本数不是“校准完成”的通行证。订阅额度百分比也不是天然可换算为统一 token 数，无法从官方或实测获得就标估计或不可得。

| 级别 | 官方或原始资料 | 本周只读这些 | 阅读预算 |
|---|---|---|---:|
| 必读复习 | [R17 · Harvard CS50 SQL](https://cs50.harvard.edu/sql/) | 聚合、筛选与查询；保持任务粒度和尝试粒度分开。 | 35 分钟 |
| 必读复习 | [R42 · Anthropic：Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) | 多次尝试、结果与回归记录的用途。 | 35 分钟 |
| 安全选读 | [R65 · OpenTelemetry：Handling sensitive data](https://opentelemetry.io/docs/security/handling-sensitive-data/) | 用量与追踪字段最小化。 | 30 分钟 |

### 实战拆解

1. 定义任务账本的数据契约，把“模型自述成功”和“本人或检查器确认成功”分开。包含失败、超时、取消与未知，不只录入令人满意的任务。

2. 对官方显示、直接测量、估算与未知分别打标签。拿不到准确调用费用或上下文长度时，保留来源与限制，不从界面猜一个精确数字。

3. 只在相近任务组内计算耗时、重试与完成情况。先检查重复记录和异常缺失，再画或计算汇总；数据太少时输出“证据不足”。

4. 设计一个简单建议规则，例如优先使用在该类低风险任务中已有可接受结果的常规档，遇到指定失败再升级。规则先人工审阅，不让模型根据一次结果不断换档。

5. 将 P3 用于下一次真实开发会话的选择与预算记录。只记录必要元数据，展示统计改进可以先不增加一次额外 LLM 调用。

### 交付与验收

| 本周交付 | 怎样确认真的完成 |
|---|---|
| 可信任务账本 | 任务与尝试清楚区分；结果和用量的来源可追溯。 |
| 带限制的汇总 | 相近任务可比较，未知与失败没有被吞掉。 |
| 一个局部建议 | 明确适用范围；数据不足时保持不推荐，而非制造精确排行榜。 |

**不用代码生成器的练习：** 自己检查一组包含重复与缺失的合成记录，解释为什么直接取平均会误导，再写正确查询。

**隐私与安全检查：** 不要读取不透明内部数据库、抓取会话凭据或绕过产品接口来获得额度。只使用官方提供、本人有权导出的信息。对任务名称和文件路径也做最小化；公开聚合仍可能暴露个人活动，不自动发布。

**落到日常生活：** 下次开工前按任务类别选择已有验证的配置，而不是默认最大强度。课后看它是否降低返工和切换成本，不把用完套餐当成收益。

**过关或补课判断：** 能够把实测、估算和未知分开，就完成 RSI 的记录层。样本不足是合格结论，不为凑数量大量制造无意义任务。

### 本周可复制的协作提示

```text
请以隐私最小化的元数据建立任务账本，区分任务、尝试、结果和用量来源。只比较相近任务，未知不填零，不伪造模型或额度。先用本地统计提出有限建议，不新增自我反思调用。
```


<a id="w20"></a>
## 第 20 周｜受控 RSI：让一次改进有假设、有预算，也可以被拒绝

> **本周要回答：** 怎样知道提示词改动真的更好，而不是仅仅更适合已经看过的那几道题？

**进入本周前：** 有一类可复现失败、有基线与评测；真实样本不足时先做明确标记的合成练习。

### 学习内容与理解目标

这里的 RSI 指受控改进循环：记录、诊断、提出候选、独立评价、人工选择。优先改一个提示片段、工具描述或来源筛选规则，不改基础模型权重。GEPA 提供反思轨迹并测试候选的研究思路；DSPy 是可选工具，但课程不要求复制论文算力或迁移语言栈。来源见 [R51 · GEPA：Reflective Prompt Evolution Can Outperform Reinforcement Learning](https://arxiv.org/abs/2507.19457)、[R50 · DSPy：官方文档](https://dspy.ai/current/)。

优化者看到的开发案例与最终保留集要分开；不断把保留集结果反馈给优化者，也会让它逐渐变成开发集。评测预算、超时、并发和所有重试应由外部执行器控制。输出更长、解释更自信或消耗更多推理，不自动等于改善。

### 学习链接与选读范围

| 级别 | 官方或原始资料 | 本周只读这些 | 阅读预算 |
|---|---|---|---:|
| 研究选读 | [R51 · GEPA：Reflective Prompt Evolution Can Outperform Reinforcement Learning](https://arxiv.org/abs/2507.19457) | 摘要、问题设定、版本信息；关注候选生成与评测思想，不照搬收益数字。 | 35 分钟 |
| 实现选读 | [R50 · DSPy：官方文档](https://dspy.ai/current/) | 程序、模块与优化器的概念，理解后再决定是否需要。 | 35 分钟 |
| 必读复习 | [R42 · Anthropic：Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) | 失败类别、可比任务与回归检查。 | 35 分钟 |

### 实战拆解

1. 选一个真实重复失败，例如引用旧版本文档。先冻结当前版本、任务集与成功标准，写出一个可证伪假设，而不是笼统要求“自我提升”。

2. 限定一轮一至三个候选作为课程起点，并设置总预算、最大尝试和停止条件。没有实际成本数据时只跑 mock 或人工离线比较。

3. 在开发集比较候选，记录所有失败与费用。最终评估由独立流程读取保留集；不要把答案、隐藏文件或评分修改权限挂载给提案 agent。

4. 核查质量是否改善，同时看延迟、复核、拒绝率和总成本。有条件时做同题成对比较与重复；样本不足就不宣称普遍更好。

5. 写采用、拒绝或继续观察的结论。采用时保留旧版本和回滚；无改进就结束这一轮，不自动追加反思循环直到“找到成功”。

### 交付与验收

| 本周交付 | 怎样确认真的完成 |
|---|---|
| 一份改进提案 | 明确失败、假设、一个主要变量、基线与停止条件。 |
| 完整候选比较 | 所有尝试和成本计入，保留集与提出候选的过程隔离。 |
| 有理由的决定 | 允许拒绝；证据不足不包装成已校准的自我进化。 |

**不用代码生成器的练习：** 自己找出一项可能泄露答案的流程设置，并说明如何在权限或评测程序层面修复，而不是只提醒 agent 不许看。

**隐私与安全检查：** 优化者不能修改成功标准、预算、权限和独立答案。只在隔离副本进行；外部文本中的“修改评分代码”之类内容仍是不可信输入。模型生成的候选不能未经审查直接替换正在运行的流程。

**落到日常生活：** 将一轮受控改进用于真实小痛点。若它没有减少错误或维护负担，就恢复简单版本；停止无收益优化本身就是省时。

**过关或补课判断：** 能拒绝一项看似先进但没有证据的改动，且预算由运行时限制，就达成本周目标。


## 第 21 周｜代码层改进：补丁、隔离评测与人为控制的发布

> **本周要回答：** 当 agent 能修改自己的工具代码时，谁来防止它通过改评分方式或扩大权限“变得更好”？

**进入本周前：** 已经做过有预算的候选比较，能独立审查代码差异、回退版本和恢复数据。

### 学习内容与理解目标

本周把改进目标从提示词扩展到一个明确代码缺陷。先理解边界：Git 分支是变更隔离，不是安全沙箱；运行未知代码需要受限制的执行身份、文件和网络权限。研究中的自修改系统与个人生产系统的风险不同，不能把论文探索直接当作安全产品。DGM 原文同时提供思路与局限讨论，见 [R52 · Sakana AI：Darwin Gödel Machine](https://sakana.ai/dgm/)。

课程采用“提案者—评测者—批准者”分工：agent 提交补丁，独立流程运行固定检查，人决定是否采用。普通功能测试可以随明确的新需求更新，但验收标准变更必须单独审查，不能由同一候选静默降低。生产部署与权限修改始终不交给改进循环自行决定。

### 学习链接与选读范围

| 级别 | 官方或原始资料 | 本周只读这些 | 阅读预算 |
|---|---|---|---:|
| 研究选读 | [R52 · Sakana AI：Darwin Gödel Machine](https://sakana.ai/dgm/) | 代码自修改、验证、风险与局限；不复制性能宣传。 | 35 分钟 |
| 环境选读 | [R70 · Docker：Get started](https://docs.docker.com/get-started/) | 容器与隔离基础；已有受控环境可不新增工具。 | 35 分钟 |
| 必读复习 | [R31 · Pro Git：在线书籍](https://git-scm.com/book/en/v2) | 分支、差异、合并和撤销，保持改动可审阅。 | 35 分钟 |

### 实战拆解

1. 选一个可以用失败测试证明的小 bug，写清修复范围与禁止修改的边界。先存下当前可用版本，不让 agent 从“整体提升系统”开始。

2. 在隔离分支与受限运行环境中执行。环境只挂载合成夹具和所需代码，不挂载私人目录、生产凭据、宿主控制接口或独立保留答案。

3. 要求补丁包含最小实现差异、相关测试和说明。检查是否偷偷改配置、删除失败案例、跳过权限校验或新增网络依赖。

4. 由独立评测流程运行检查，并人工复核至少一条关键结果。自动通过不等于已经安全，尤其是运行时权限、数据流和业务动作。

5. 人工选择合并或拒绝。采用后只做小范围试运行，并实际演练回退；不允许 agent 自行连续部署下一版。

| 本周交付 | 怎样确认真的完成 |
|---|---|
| 可审查补丁 | 范围明确，没有夹带权限、预算与评分标准的隐蔽变化。 |
| 隔离评测记录 | 说明实际运行环境和限制，不把分支称为安全沙箱。 |
| 合并或拒绝与回退 | 决定有证据，恢复步骤经过操作。 |

**不用代码生成器的练习：** 自己审查一份包含无关配置变更的补丁，指出为什么应拆分或拒绝；然后独立回退已合并的测试改动。

**隐私与安全检查：** 容器也可能通过过宽挂载、特权模式或宿主接口失去隔离意义。不要给改进 agent 生产秘密和不必要网络，不能把“它不会这么做”的提示当访问控制。环境风险不明确时，只做补丁提案，不执行未知代码。

**落到日常生活：** 把一个经常打断使用的小错误修好，而不是为了展示 RSI 不断重构。后续一周观察维护是否减少；不要把增加测试和基础设施本身当生活收益。

**过关或补课判断：** 能独立识别越界变更，知道何时拒绝执行并完成回退，才具备受控代码改进的基础。


## 第 22 周｜第二位用户：观察任务、得到同意、完成交接

> **本周要回答：** 当使用者不理解你的实现，也没有你在旁边提示时，工具仍能完成任务吗？

**进入本周前：** 至少一个项目能够运行、停止与恢复，具备合成演示数据和清楚的数据说明。

### 学习内容与理解目标

个人 FDE 的下一步不是扩大用户数量，而是验证自己的理解是否能够被别人使用。邀请一位知情同意的人，在合成数据上完成一个真实形式的任务；对方可以随时停止，不必提供私人资料。无法邀请时，用自己隔几天再做一个陌生任务作为弱化替代，并诚实说明没有外部用户验证。

观察行为比询问喜好更有用：哪里停住、哪句话理解错、哪里不敢点、遇到错误会怎么办。不要为了让测试“成功”不断在旁边指路。交接需要上手、数据、费用、限制、停止和恢复，而不仅是产品介绍。方法参考 [R75 · GOV.UK Service Manual：Moderated usability testing](https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing) 与 [R76 · GOV.UK Service Manual：Getting users’ consent for research](https://www.gov.uk/service-manual/user-research/getting-users-consent-for-research)。

### 学习链接与选读范围

| 级别 | 官方或原始资料 | 本周只读这些 | 阅读预算 |
|---|---|---|---:|

| 选读 | [R08 · MIT Missing Semester：Beyond the Code](https://missing.csail.mit.edu/2026/beyond-code/) | 维护、协作与交接相关材料。 | 35 分钟 |

### 实战拆解

1. 写一段易懂邀请：测试目的、预计占用、仅使用合成数据、是否记录、如何退出。未经额外同意不录音、不录屏、不收集账号或联系信息。

2. 准备一个任务而不是操作指南，例如“安排三项活动并导出检查”。提供必要目标，不告诉每个按钮在哪里，让界面自己承担解释责任。

3. 记录观察而非评价：停顿、误操作、问题、能否恢复。避免“用户不懂技术”这种没有改进指向的结论。

4. 只修复一个影响最大的障碍，再让对方或一个新的合成任务验证。没有必要从一位用户的偏好推断所有人的需求。

5. 写一页交接说明，包含运行、数据去向、费用、限制、导出清除、停止恢复与版本。公开反馈仅保留经同意的匿名概要。

### 交付与验收

| 本周交付 | 怎样确认真的完成 |
|---|---|
| 知情同意与观察方案 | 明确记录范围和退出方式；不要求真实私人资料。 |
| 真实反馈或替代说明 | 区分外部观察与自测，不伪造用户评价。 |
| 一页交接说明 | 陌生使用者能知道如何开始、停止和处理错误。 |

**不用代码生成器的练习：** 独立重写一条被用户误解的提示，并用新情景验证；不要只把文字变得更长。

**隐私与安全检查：** 去掉姓名并不一定匿名，职业、时间、任务和截图仍可能识别个人。公开报告优先使用合成重现，不上传访谈原文、音视频或私人日志。工作场景试用需另走组织批准流程。

**落到日常生活：** 观察工具是否减少解释负担。未来的自己也是“第二位用户”：一段时间后仍能理解、修复和停用，才是真的可维护。

**过关或补课判断：** 至少一个高价值问题被观察并改善，交接说明可用，就达成目标。没有受试者时保留限制，不强求招募。



<a id="w23"></a>
## 第 23 周｜价值审计：计算净省时，也允许删除自己的作品

> **本周要回答：** 这个工具究竟让生活更轻松，还是把原来的工作换成了监督模型和维护系统？

**进入本周前：** 有实际使用和维护记录，知道哪些结果是实测、估计、未知与合成演示。

### 学习内容与理解目标

价值要按相同任务和相近完成质量比较。计入新流程中自己的操作、监督、复核、返工和维护，包括失败尝试；模型在后台运行而你可做其他事情的时间，不能全部算作你的劳动。一次性建造、现金支出与持续运行分开记录。

省时不是唯一价值，减少遗漏、提高可追溯性和形成独立能力也重要，但应分别描述。学习实验可以暂时不回本，前提是清楚标成学习投入。最困难的工程决定常常不是加功能，而是停止一个没有人在用的系统。

### 学习链接与选读范围

| 级别 | 官方或原始资料 | 本周只读这些 | 阅读预算 |
|---|---|---|---:|
| 必读复习 | [R17 · Harvard CS50 SQL](https://cs50.harvard.edu/sql/) | 汇总可比任务，检查分母和缺失。 | 30 分钟 |
| 选读复习 | [R67 · Google SRE：Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/) | 从用户结果而非系统热闹程度看质量。 | 30 分钟 |
| 选读复习 | [R74 · GOV.UK Service Manual：Plan user research](https://www.gov.uk/service-manual/user-research/plan-user-research-for-your-service) | 回到最初问题，检查需求假设是否成立。 | 30 分钟 |

### 实战拆解

1. 为 P1、P2、P3 分别列出实际使用次数、完成结果、主动时间、复核与维护。空白就写无记录，不能根据模型运行时长倒推出人的省时。

2. 计算每周净省时：可比成功任务在旧流程中的主动时间，减去新流程所有操作、复核、失败返工和维护。未完成的需求另外列出，避免把任务变少误算成效率提升。

3. 单列建造时间、订阅增量支出、API 和托管费用。原来就为其他用途购买的订阅可说明分摊假设，不把同一笔费用重复归因。

4. 做保留、简化、暂停或删除决定。没有使用的功能先移出主流程；净省时为负但学习价值明确的项目可以继续，但要限制投入。

5. 给节省的时间一个具体去处，例如一段专注学习、运动或休息。不要把所有余量再投入无上限模型比较与工具维护。

### 交付与验收

| 本周交付 | 怎样确认真的完成 |
|---|---|
| 一份真实价值报告 | 实测与假设分开，失败和维护没有被排除。 |
| 清楚的保留决定 | 至少一个功能经过必要性审查，可以决定不删除但要有理由。 |
| 下月实际使用计划 | 明确自然触发与维护上限，而不只是产品路线图。 |

**不用代码生成器的练习：** 自己用一组含失败和维护的合成数据计算净省时，解释为什么“模型生成用了两分钟”不能直接当作节省的人力。

**隐私与安全检查：** 个人使用频率、时间戳和任务类别可能暴露生活规律。对外展示时用经过检查的汇总或合成例子，说明样本与方法；不要把私人原始账本作为作品集附件。

**落到日常生活：** 回看课程第一周记录的摩擦，确认它是否真的改变了。把没有价值的提醒、定时任务、连接器和云资源停掉，并撤销不再需要的权限。

**过关或补课判断：** 报告能够支持一个真实取舍，且本人承认投入与限制，就达标；净省时为负并不是必须掩饰的失败。

### 本周可复制的协作提示

```text
请只依据实际记录做价值审计，保留失败、复核和维护，并把建造时间与现金费用单列。未知不估成精确收益。对每个项目给保留、简化或暂停的证据，不默认继续扩展功能。
```

## 第 24 周｜毕业不是终点：新任务、独立修复与可更新的能力体系

> **本周要回答：** 面对一个没有做过的小需求和一次故障，你能从需求走到恢复，而不只是重复课程示范吗？

**进入本周前：** 至少一个确定性工具、一个受控 agent 流程和一次有证据的改进试验；未完成部分如实保留。

### 学习内容与理解目标

毕业标准是端到端能力，不是视频数量或 agent 数量。选择一个此前未实现的小需求，说明范围、输入、权限和成功标准；完成实现、相关验证、实际使用与恢复。另一项要求是在没有代码生成器代做的情况下完成一次小修复，允许查文档。

<a id="deployment"></a>
## 六、部署能力的补充说明：把“能访问”与“能放心使用”分开

### 1. 两条可落地路线，选择一条即可

**路线 A：本地个人工具。** 使用本机运行环境、明确的工作目录和手动触发；需要调度时使用自己理解的系统机制。必须知道电脑休眠、关机、断网和账号退出时会发生什么。模型推理若通过云端完成，应在数据流图上明确标出；“执行器在本地”不代表“所有数据都在本地”。本地路径降低了部分部署负担，但不自动解决设备共享、备份、同步和模型服务的数据处理问题。

**路线 B：受控托管服务。** 先发布最小 mock 服务，再验证认证、对象权限与状态保存，然后接少量只读模型调用，最后才考虑定时运行。[R71 · Render：Deploy a Node Express App](https://render.com/docs/deploy-node-express-app) 是一个具体 Node 托管实例，不是必须购买的服务；已有平台可以继续使用。每次实施时核对计划价格、运行时间、持久存储、区域、日志和访问控制，不假定免费套餐适合长期后台任务。

路线 B 不应把数据库文件放在可能被重建的临时磁盘上。不同服务类型的存储与调度限制分别检查；例如 [R72 · Render：Cron Jobs](https://render.com/docs/cronjobs) 和 [R73 · Render：Persistent Disks](https://render.com/docs/disks) 不能被合并理解成“所有任务都能挂一块永久盘”。对于个人练习，使用低频只读任务与可控存储比过早搭建复杂基础设施更重要。

### 2. 上线前必须回答的九个问题

| 问题 | 应提供的证据 |
|---|---|
| 运行在哪里、用什么身份？ | 运行环境与身份说明，而不是只有一个网址 |
| 谁能触发与读取结果？ | 未登录、无权限与错误对象访问的实际拒绝测试 |
| 数据去了哪里？ | 输入、输出、模型、日志、备份的去向与保留策略 |
| 如何产生和结束任务？ | 明确触发、取消、总超时与卡住后的处理 |
| 重试是否导致重复动作？ | 重复和并发样例；不确定完成状态的核查路径 |
| 费用如何计量与限制？ | 各计费账户、预算来源、覆盖重试的执行限制 |
| 如何发现真正失败？ | 用户结果检查，而不仅是进程存活或 HTTP 状态 |
| 如何恢复？ | 实际回滚与备份恢复记录，以及可能丢失的数据范围 |
| 如何彻底停用？ | 停调度、清队列、撤销凭据、处理数据与外部产物的方法 |

这不是一张“填写后就安全”的认证表。风险与控制需要结合具体运行环境测试；组织系统与高后果场景应由有权限的责任人审查。一般风险识别可参考 [R66 · NIST：AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework)。

### 3. 动作权限逐级增加

| 等级 | 示例 | 课程默认要求 |
|---|---|---|
| L0 不执行外部动作 | mock、本地合成文件、离线统计 | 第 1 周即可开始，避免覆盖源数据 |
| L1 只读公开来源 | 从固定文档提取证据 | 来源与网络范围明确，输出可追溯 |
| L2 草稿 | 提醒文本、计划草案、拟议补丁 | 人工检查，不直接发送或合并 |
| L3 可逆写入 | 专用测试日历的一条事件 | 按对象与内容批准，有重复检查、撤销和审计 |
| L4 高后果动作 | 付款、永久删除、生产权限变更 | 不进入本课程默认自动化范围 |

限制落实在执行器与服务端权限，不只写在自然语言里。认证回答“你是谁”，授权还要回答“你能对这个对象做什么”；相关原则见 [R60 · OWASP：Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。不能通过隐藏按钮、秘密网址或 CORS 代替授权。

<a id="costs"></a>
## 七、有高额度订阅，仍要分清三笔账

### 1. 订阅、应用推理与托管不是同一份预算

| 预算 | 典型用途 | 需要核对什么 |
|---|---|---|
| coding 订阅 | 交互式开发、学习、官方支持的个人自动化 | 认证方式、可用工具、共享额度、限制窗口、额外消费设置 |
| 应用 API | 自己部署的应用调用模型 | 真实项目与密钥、计费单位、预算、重试和并发 |
| 托管与存储 | 服务、任务调度、数据库、日志 | 运行计划、持久性、网络与日志费用、停用后是否继续产生费用 |

OpenAI 的 ChatGPT 与 API 计费需要分别管理；Codex 支持路径应按当前官方入口核对，不能从一句“订阅可用”推出所有应用都可共用额度。来源见 [R53 · OpenAI：ChatGPT 与 API 的计费管理](https://help.openai.com/en/articles/9039756-managing-billing-for-chatgpt-and-the-api-platform)、[R54 · Codex 使用与计费入口](https://developers.openai.com/codex/pricing/)。

Claude 也需要区分订阅认证与 API key 路径。核对日的 Agent SDK 说明页在 June 15 更新中写明此前拟议改制暂停，相关使用仍计入订阅；页面保留的旧月度 credits 公告不能当作现行余额。这是带日期的产品状态，不是未来承诺。实施前重新核对 [R55 · Claude Code：Use with your Pro or Max plan](https://support.claude.com/en/articles/11145838-use-claude-code-with-your-pro-or-max-plan)、[R56 · Claude Agent SDK：Use with your Claude plan](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)。

本课程不通过复制登录令牌、转售共享账号、建立未授权中转或绕过限额来利用订阅。也不把产品界面的“5x”解释成跨厂商固定 token 数；它只是需要回到对应产品说明核对的套餐表述。

### 2. 一套与两套订阅怎样安排

只有一套时，优先用于主力开发与导师反馈，分开任务会话，并保留处理故障和补课的余量。有两套时，可将第二套用于关键设计、重要补丁与难故障的独立复核；不要让两个 agent 无边界互相争论，也不要把额度用尽当成成功指标。

常规任务先用在自己的同类任务中已验证可接受的模型与配置。困难设计、跨模块故障或高风险边界再提升推理投入。不同产品的 effort 名称和实现并不天然等价，记录实际配置即可，不制造一张永久有效的“最佳强度表”。

### 3. 把预算限制真正落实

先用 mock 检验停止逻辑。真实运行至少限制总任务时间、工具步骤、重试、并发与可授权费用；控制应覆盖所有子调用，而不是只算最后一次成功。预算不足时停止或进入人工批准，不静默切换到更贵配置。供应商预算提醒未必是严格硬限制，需确认实际计费与限额行为。

配置样例中的“最多 10 步、最多 2 次重试”只是教学起点，不是行业标准或安全保证。只有执行程序真的读取、落实并通过测试后，才能称为有效控制。并发请求还需要在共享预算与运行状态层面协调，不能让每个进程都各自认为有整份预算。

<a id="rsi"></a>
## 八、RSI 的四层边界：改进系统，不神化“自我进化”

| 层 | 实际行为 | 主要学习价值 | 不该宣称什么 |
|---|---|---|---|
| R0 记录 | 保存任务元数据、实际结果和失败 | 建立可追溯经验 | 不能把模型自述当成功 |
| R1 统计 | 估计同类任务耗时、重试和配置适用性 | 根据真实观察调整选择 | 不能把少量样例叫普遍校准 |
| R2 候选优化 | 提出有限提示或工具变更，独立评测 | 用证据采用或拒绝 | 不能只看最好的尝试 |
| R3 代码提案 | 在隔离环境生成补丁，人审查发布 | 形成受控工程改进 | 不能自动改权限、预算和评分标准 |

GEPA 与 DGM 为后期选读提供了研究入口，但它们的具体设定、评价与约束不能直接等同于个人系统的效果。这里不复述未经本人复现的性能结论，更不据此声称自主无限进化已实现。原始来源见 [R51 · GEPA：Reflective Prompt Evolution Can Outperform Reinforcement Learning](https://arxiv.org/abs/2507.19457)、[R52 · Sakana AI：Darwin Gödel Machine](https://sakana.ai/dgm/)。

一次有效改进试验可以非常小：原系统常引用旧版文档；先冻结基线，提出“版本过滤会减少旧引用”的假设；只改变过滤规则；在相同任务、预算与权限下比较；用独立案例验证；记录额外成本；人决定采用或拒绝。没有改善就停止，不再启动一轮反思试图把结论改成成功。

三类控制不应交给候选提出者自行修改：**成功标准、权限与预算、最终独立评价的答案。** 如果任务真的要求更改验收，应把规则变更作为单独决定审查，而不是夹在代码补丁里。

保留集不是永远可重复使用的秘密宝箱。随着反馈积累，它可能逐渐进入优化过程；需记录使用历史，必要时增加独立新案例。小样本只支持小范围判断。没有足够真实数据时，最诚实的产物是一份错误分类和下一步采样计划，而不是精确到小数点的可靠性承诺。

<a id="habits"></a>
## 九、从知识到生活：让工具有自然触发点，也有退出机制

### 1. 不让知识工作台变成新闻仓库

每周只选一到三个真正与当前问题有关的知识点。为每个知识点完成：**来源、解释、适用条件、反例、预测、实验、行为改变、再次应用。** 没有实际问题时可以不增加资料，不要求系统每天生成内容证明自己在运行。

例子：你学到幂等性，不只保存定义，而是在测试环境重复触发一次任务，观察是否产生重复草稿，改变实现，再用另一个输入验证。你读到新的上下文方法，不立即重建记忆平台，而是比较一次短交接与原流程，确认恢复任务是否真的更容易。

这些例子是课程练习，不代表对任何具体人的实测结果。提醒和复测应围绕自然任务触发，避免额外增加每天维护多个面板的义务。

### 2. 净省时的计算方式

```text
每周净省时
= 可比成功任务在旧流程中的本人主动时间
− 新流程所有本人操作、监督、复核与返工时间（包括失败）
− 本周维护时间
```

一次性建造时间、现金费用、未完成需求和主观质量变化另外记录。模型在后台运行而你可以做别的事情，不等于你在持续劳动；但你被迫等待、频繁检查和处理错误的时间也不能漏掉。

**纯合成算例：** 同等完成质量下，每周 12 项任务原来每项主动花 6 分钟，共 72 分钟。新流程全部主动操作与复核 18 分钟，维护 14 分钟，净省 40 分钟。假设建造耗时 8 小时且未来情况稳定，简单时间回本为 480 ÷ 40 = 12 周。这里没有计入现金费用、学习价值与未来故障，不是读者的收益预测。

净省时长期为负时有四种合理动作：缩小任务、降低频率、回到手动、停用。学习项目可以继续，但应明确是学习预算。课程的成功不是所有工具永远在线，而是你能辨别什么值得留在生活里。

<a id="safety"></a>
## 十、隐私与安全贯穿全程，而不是最后加一句免责声明

### 1. 数据分级：从默认不上传开始

| 数据类型 | 本课程默认处理 |
|---|---|
| 合成样例、公开官方材料 | 可用于练习；仍检查版权、来源和不可信内容 |
| 个人普通资料 | 先最小化与本地处理；发送到外部服务需明确目的、权限与数据政策 |
| 他人资料、工作或客户资料 | 不进入默认实验；需要相应授权、组织批准与适用处理流程 |
| 凭据、私人密钥、会话令牌 | 不写入文章、代码、提示、截图、日志或公开仓库 |
| 高后果敏感数据与生产操作 | 超出默认课程范围，另做专业与责任审查 |

换成匿名 ID 只是减少直接标识，不必然达到匿名。日期、地点、职业、任务内容和行为模式仍可能形成关联。公开作品优先使用合成重现，不自动发布真实元数据的聚合。一般风险识别可参考 [R66 · NIST：AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework)，秘密与日志处理分别见 [R59 · OWASP：Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)、[R61 · OWASP：Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)。

### 2. 常见误区与需要验证的控制

| 误区 | 更可靠的处理方式 |
|---|---|
| “程序在本地，所以没有云端数据流” | 检查模型调用、开发工具、遥测、备份与同步，而不只看主程序 |
| “只读 agent 没有风险” | 控制能读什么、能发往哪里，以及返回和日志是否包含私人内容 |
| “MCP 服务安装后就可信” | 核对来源、权限、令牌、工具返回和实际访问范围；见 [R57 · MCP：Security Best Practices，2026-07-28 版](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices) |
| “系统提示禁止越权就足够” | 执行器和权限系统实际拒绝越界；用合成注入与越界参数测试 |
| “没有人知道链接就算私密” | 使用真正认证与对象授权；未授权会话实际访问测试 |
| “分支或容器自动等于安全沙箱” | 检查执行身份、挂载、特权、网络与宿主控制接口 |
| “删除最新文件就修复密钥泄露” | 先撤销或轮换，再处理历史、副本与日志；见 [R64 · GitHub：Removing sensitive data from a repository](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository) |
| “网站上线就是 agent 部署完成” | 验证运行、状态、触发、费用、停止、恢复和真实结果 |

不可信资料可能通过提示注入诱导模型偏离任务，防护需要多层边界，不存在一句万能提示。相关参考见 [R58 · OWASP：LLM Prompt Injection Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)。服务端抓取还需要限制目标、重定向和网络访问，不能把任意链接直接交给后端读取；见 [R62 · OWASP：Server-Side Request Forgery Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)。这些指南是设计起点，不是系统经过专业安全审计的证明。

### 3. 第三方依赖也是数据与执行边界

新装包、插件、浏览器扩展或 MCP 服务之前，先确认来源、必要性、维护状态与所需权限。只因模型建议就运行安装脚本，不算理解依赖。锁定已经验证的版本并保留更新记录，但安全修复不能无限延期。

日志不应该默认收集所有东西。运行标识、状态、错误类别和必要用量通常比完整提示更适合开始；要诊断确实需要原文时，再明确访问、期限与脱敏。第三方遥测也是外部数据接收方，参考 [R65 · OpenTelemetry：Handling sensitive data](https://opentelemetry.io/docs/security/handling-sensitive-data/)。

<a id="update-policy"></a>
## 十一、怎样更新课程，而不被新模型拖着走

### 1. 稳定能力与可替换实现分开

约八成注意力给需求、代码、数据、网络、验证、权限和维护；约两成用于模型、SDK 与部署适配。这只是精力安排建议，不是精确研究结论。替换一个 API 不应该要求重学整个项目；将模型配置、工具接口与业务规则分开维护。

每条更新记录至少包含来源、发布或版本日期、核对日期、影响的任务、成本与权限变化、验证计划、回滚方法。模型 ID 和推理设置必须从实际产品或官方文档核对，不用宣传名称猜测调用参数。

### 2. 三个更新窗口

| 节奏 | 执行内容 | 停止条件 |
|---|---|---|
| 每周 20–30 分钟 | 看相关官方课程、模型、SDK 和安全通知，最多记三条采用/观察/忽略建议 | 没有影响当前任务的变化就结束 |
| 每月一个有预算实验 | 用固定任务比较一个新旧方案，记录所有成本与回归 | 无明确收益就保持现状 |
| 重大安全或弃用事件 | 检查实际影响、暂停受影响能力、做必要修复 | 验证恢复后结束，不顺便重写全项目 |

这是一套维护方案，不代表已经替读者创建自动任务。要自动执行时另设运行环境、来源、权限和费用；自动检查只生成提案，不自动安装依赖、修改课程或升级生产系统。

### 3. 哪些理由不足以触发迁移

模型发布会、公共排行榜单项领先、别人社交媒体演示、工具宣称“一键全部完成”，都不足以单独证明你的任务应迁移。相反，原流程的具体失败被解决、同等质量下减少复核、必要安全更新、官方弃用和可维护性改善，才值得进入自己的验证过程。

还要问“旧机制是否可以删除”。用于补偿旧模型行为的复杂上下文处理或特殊重试，可能在新环境中变成负担；[R46 · Anthropic：Managed Agents 工程文章](https://www.anthropic.com/engineering/managed-agents) 提供相关工程讨论，但具体是否删除仍取决于自己的测试。

<a id="publishing"></a>
## 十三、把学习成果写成技术博客：公开方法，不公开私人记录

### 1. 文章应该展示什么

围绕“问题—约束—实现—验证—失败—采用或拒绝”组织叙事。用合成样例展示数据流，引用官方文档与研究，写清实际执行范围与限制。尚未完成的内容使用“计划”“练习”或“待验证”，不要改成作者亲身成功的故事。

完整课程可以作为一篇长文；也可以将每周拆成单篇系列。分周发布时保留适用对象、前置能力、资料核对日期和安全要求，让单篇读者不必翻到总纲才知道关键边界。外部课程链接保留来源，不上传其整套课件、付费视频、受限实验或未获许可素材。

### 2. 发布前内容检查

检查正文、代码块、附件、截图、图片元数据、压缩包、网页源码与版本历史。移除个人姓名、邮箱、真实域名或仓库身份、雇主客户信息、日历细节、财务健康资料、登录信息、私人文件路径、日志与聊天记录。项目可以保留架构思想，但公开案例改成通用名字和合成数据。

确认示例代码没有真实服务地址或凭据，公开配置默认 mock、只读和未授权状态。带有真实数据的表格、数据库、备份与源映射文件不应混进静态公开目录。私有系统截图建议用合成界面重现，不依赖一层可撤销遮挡。

秘密一旦公开，先撤销或轮换，再按 [R64 · GitHub：Removing sensitive data from a repository](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository) 处理历史与副本。内容扫描只能减少明显遗漏，不能保证识别所有可关联信息，也不能证明代码经过完整安全审计。

### 3. 教程页与运行中的 agent 分开托管

教程展示不需要访问读者邮箱、日历、文件或模型账号。优先静态正文，不附带登录、上传、执行按钮和追踪脚本。运行演示需要另一个明确隔离的环境，默认合成数据、最小权限与独立预算，不能把个人生产接口直接暴露在文章里。

本文配套 HTML 不主动加载第三方脚本、字体、图片、统计或嵌入内容；官方资源仅作为可点击链接。它并不能替你的既有网站移除分析代码、Cookie、CDN 访问日志或主机日志；把 Markdown 粘进已有站点之后，要再次检查最终页面的数据流。

## 结语：让技术成为可以依赖、也可以退出的能力

这条路线的毕业成果，不是二十四个演示，也不是一个永远自我改写的庞大 agent。更理想的结果是：有两三个工具自然进入日常，有一套面对新知识的判断与实验方法，有能力解释核心代码、验证结果、接管故障，并有证据知道哪些东西值得继续保留。

不需要把所有生活都自动化。把重复劳动交给可靠的工具，把重要决定、学习理解与是否继续使用的权利留给自己。

**课程设计不是学习效果保证，静态教程不是系统安全认证，公开分享也不需要牺牲隐私。** 从一个低风险真实问题开始，交付最小成果，亲自使用，然后再决定下一步。
