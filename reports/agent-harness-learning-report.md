# Agent Harness 开源项目学习报告

更新日期：2026-08-08

用途：为后续 Harness 理论、实现练习和 `course.html` 在线课程提供研究底稿。

## 1. 结论先行

Agent Harness 不是一个更长的系统提示词，也不是给模型套一层聊天界面。它是把模型能力变成可重复工作结果的运行系统，至少要同时管理：上下文、工具、执行状态、权限、失败恢复、评测与反馈。

最有学习价值的代码库并不一定功能最多。建议按下面的顺序学习：

1. **mini-SWE-agent**：先看最小循环，理解模型、环境、工具和停止条件的边界。
2. **Pi / pi-mono**：学习多模型适配、轻量上下文、工具调用和可扩展运行时。
3. **OpenAI Codex**：学习沙箱、审批、项目指令、会话状态、进程控制和真实产品约束。
4. **LangGraph**：专门学习可恢复执行、检查点、人工介入和副作用幂等。
5. **OpenMinis**：学习端侧沙箱、设备权限、技能按需加载和移动端 Agent 产品化。
6. **OpenPencil**：学习领域专用 Harness 如何把自然语言变成结构化、可验证的设计动作。
7. **CodePilot**：学习多提供商桌面外壳、MCP、技能、远程桥接与用户工作区组织。
8. **OpenHands / Agent SDK**：最后观察从单机循环走向可扩展执行平台的工程边界。

我的独立判断是：**先学小循环，再学恢复与权限，最后学多智能体和复杂 UI。** 如果一个项目无法展示任务终态、可重放轨迹、权限边界和失败恢复，功能再多也只能算 Agent Demo，而不是可靠 Harness。

## 3. 统一审查框架

每个 Harness 用九个维度审查，避免被功能清单误导。

| 维度 | 必问问题 | 合格证据 |
|---|---|---|
| 循环 | 谁决定继续、停止、追问或移交？ | 明确状态机、终态与等待态 |
| 上下文 | 什么进入模型，什么时候压缩或淘汰？ | 可检查预算、裁剪策略与污染测试 |
| 工具 | 参数、返回值和失败怎样约束？ | 有类型契约、超时、取消与错误分类 |
| 状态 | 进程退出后怎样恢复？ | 检查点、事件日志、重放与版本迁移 |
| 副作用 | 重试会不会重复付款、写库或发消息？ | 幂等键、事务边界与补偿动作 |
| 权限 | 模型能看到和做到什么？ | 最小权限、沙箱、审批与审计 |
| 评测 | 成功由谁定义？ | 环境终态检查、多次试验与失败分类 |
| 可观测性 | 为什么成功或失败？ | 结构化轨迹、工具耗时、成本与资源指标 |
| 反馈 | 现场失败如何改善 Harness 或模型？ | 可追踪缺陷、回归集与版本对照 |

## 4. 推文中三个公开可核验项目

### 4.1 OpenMinis — 端侧 Agent 的权限与沙箱样本

仓库：<https://github.com/OpenMinis/OpenMinis>

值得学习：

- iOS 与 Android 端侧 Linux 环境；把“工具执行”放进真实但受限的操作系统，而不是伪造函数结果。
- Health、Calendar、Reminders、Contacts、HomeKit、Bluetooth 等设备能力作为工具，天然要求细粒度授权与用户意图校验。
- `SKILL.md` 按需加载：元数据常驻，上下文只在命中任务时载入，适合研究渐进式上下文披露。
- 工作区、持久记忆、浏览器自动化与原生系统入口共同形成真实的长期 Agent 产品。

应重点审查：

- 设备工具的授权能否按资源、目的和动作细分，而不只是一次性总开关。
- Linux 沙箱与宿主设备能力之间是否存在越权桥接。
- “私有、端侧”不等于“无风险”；本地持久记忆仍需删除、导出、隔离和污染恢复。
- 仓库是私有开发树的镜像且不接收 PR，适合阅读与复现实验，但不适合作为开放协作流程样板。

推荐实验：设计一个“把群聊行动项写入提醒事项”的权限矩阵，注入恶意群消息，验证模型可以读取文本但不能静默创建高影响事项。

### 4.2 CodePilot — 桌面多模型外壳与工作区编排样本

仓库：<https://github.com/op7418/CodePilot>

值得学习：

- 多模型提供商与自定义端点的统一配置，适合比较协议差异怎样泄漏到 Agent 行为。
- Code / Plan / Ask 模式把行动权限显式暴露给用户。
- MCP 与 Skills 分开管理，有助于理解“能力接口”和“行为方法”不是同一层。
- `soul.md`、`user.md`、`claude.md`、`memory.md` 展示人格、用户偏好、运行指令与记忆的文件化组织。
- Telegram、飞书、Discord、QQ、微信等远程桥接带来跨端身份、重放与确认问题，具有很高的安全研究价值。

应重点审查：

- 高级文件编辑与终端能力依赖外部 Claude Code CLI；应区分 CodePilot 自身 Harness 能力与下游 Harness 代理能力。
- 桌面签名、未公证或未签名构建对供应链信任的影响。
- 多提供商“能调用”不代表行为等价；工具选择、思考模式、上下文缓存和流式事件都需要契约测试。
- 远程桥接必须绑定用户、设备、会话和高影响动作确认，不能只依赖聊天账号登录。

推荐实验：用同一任务、同一工具、同一上下文预算比较三家模型，记录工具协议错误、无效重试、上下文膨胀和最终环境结果，而不是只比较回答观感。

### 4.3 OpenPencil — 领域专用 Harness 的最佳样本

仓库：<https://github.com/ZSeven-W/openpencil>

值得学习：

- 设计对象不是自由文本，而是可序列化 `.op` 文档与有类型的编辑命令；环境结果可机器验证。
- 分层流程 `design_skeleton → design_content → design_refine` 把复杂设计拆成不同约束的阶段。
- 并行 Agent Teams 按空间分区委派，属于可解释的独立并行，而不是给同一上下文套多个角色名。
- MCP、CLI、无头服务器和实时画布共享同一领域模型，是“一个执行内核、多种交互表面”的参考架构。
- 模型能力配置会按模型层级调整提示、思考模式和超时，适合研究 Harness 与模型的耦合。
- Git 友好文档、三方合并和字段级冲突解决，使 Agent 产物进入可审查的软件协作流程。

应重点审查：

- 多 Agent 在同一画布写入时的冲突隔离、合并语义与失败回滚。
- “反套路”或风格多样性不能只靠提示，应有结构、视觉和用户偏好的可量化评测。
- 自动代码生成需要验证语义、可访问性、响应式和视觉差异，不应把“能导出”当作“能交付”。
- README 显示项目经历了从 TypeScript/Electron 到 Rust 的大迁移；学习时要以当前主干为准，避免把旧架构结论混入现状。

推荐实验：让三个 Agent 分别设计导航、内容和页脚；主动制造共享设计变量冲突，比较最后写入覆盖、CRDT、三方合并和“由评判者裁决”四种策略。

## 5. 补充的高价值第一方开源项目

### 5.1 mini-SWE-agent — 最小可读基线

仓库：<https://github.com/SWE-agent/mini-swe-agent>

学习目标：在尽量少的代码里分清 Agent、Model、Environment 和 Run Script。它是所有复杂 Harness 的对照组：如果复杂框架不能在相同模型、工具和预算下显著胜过它，就不应承担额外复杂度。

### 5.2 Pi / pi-mono — 轻量而完整的可扩展内核

仓库：<https://github.com/badlogic/pi-mono>

学习目标：统一多提供商 API、工具调用与状态管理、编码 Agent CLI、TUI/Web UI 分层、扩展与上下文文件注入。特别适合研究“核心循环保持小，能力通过边界扩展”的设计。

### 5.3 OpenAI Codex — 真实产品约束下的 Harness

仓库：<https://github.com/openai/codex>

学习目标：Rust 运行时、沙箱执行、审批、项目指令、技能、会话、记忆、进程与远程环境协议。研究时应以代码、测试和文档为准，不把模型在对话中对自身 Harness 的猜测当事实。

### 5.4 LangGraph — 可恢复执行专项

仓库：<https://github.com/langchain-ai/langgraph>

学习目标：持久状态、检查点、人工中断、恢复与副作用封装。它适合作为“执行语义课程”，但图结构本身不自动带来正确性；仍需任务终态检查、幂等和权限边界。

### 5.5 OpenHands / Agent SDK — 平台化执行

仓库：<https://github.com/All-Hands-AI/agent-sdk>

学习目标：从单任务循环走向 SDK、隔离运行环境、并发和部署平台。进入这个项目之前，应先能自己写出最小 Agent 循环，否则容易只会拼装接口。

## 6. 不建议优先投入的项目类型

- 只有多角色提示，没有独立上下文、独立工具或独立判断的“多智能体”。
- 只有 UI 和模型切换，没有状态、恢复、权限、评测的“Agent 客户端”。
- 把向量数据库直接命名为“长期记忆”，却没有时效、授权、冲突和删除语义的项目。
- 只报告单次 benchmark 分数，不公开 Harness、资源上限、重复次数和失败样本的项目。
- 默认开放 shell、网络、密钥和文件系统，再依赖模型“自觉”的项目。

## 7. 八周实践路线

### 第 1 周：最小循环

- 复刻 mini-SWE-agent 风格的循环，限制在 120 行以内。
- 工具只有 `read_file`、`search_text`、`apply_patch`、`run_test`。
- 证据闸门：能解释每一种终态、每个错误如何回到模型、何时停止。

### 第 2 周：工具契约与协议差异

- 接入两家模型提供商，保持工具 schema 一致。
- 注入畸形 JSON、重复 tool call、流中断和不支持的 `tool_choice`。
- 证据闸门：输出兼容性矩阵和确定性回归测试。

### 第 3 周：持久状态与恢复

- 把会话事件写成仅追加日志，定期快照。
- 在工具执行前、执行后、结果回传前分别杀死进程。
- 证据闸门：恢复后不重复已确认副作用，且可解释恢复位置。

### 第 4 周：权限与沙箱

- 为工具增加租户、资源、动作、目的和期限约束。
- 在 HTML、PDF、工具描述和记忆中植入间接提示注入。
- 证据闸门：Agent 可以读到攻击，但无法越过文件、网络和审批边界。

### 第 5 周：上下文与记忆

- 比较完整历史、摘要、检索和执行状态树。
- 注入过时事实、相互矛盾记忆和被污染摘要。
- 证据闸门：报告任务成功率、时效错误、令牌成本与污染恢复。

### 第 6 周：领域 Harness

- 仿照 OpenPencil，把一个业务领域建成有类型对象、动作和不变量。
- 模型只能提出动作，运行时验证并执行。
- 证据闸门：非法状态无法由提示绕过，所有动作可审计和回滚。

### 第 7 周：评测与多智能体消融

- 建立 60 个来自真实失败的任务，至少重复三次。
- 比较单 Agent、固定多 Agent、动态委派三种实现。
- 证据闸门：用环境结果、延迟、成本、协调失败和轨迹清晰度选出帕累托方案。

### 第 8 周：端到端交付

- 向 5–10 个用户灰度一个只读 Agent，再开放一个可逆动作。
- 完成监控、回滚、事故演练、采用率和人工改写率测量。
- 证据闸门：陌生操作员仅靠运行手册恢复服务，用户能说出被改变的工作结果。

## 8. 后续理论路线

后续课程应围绕五个可证伪命题展开，而不是围绕产品名称：

1. **绑定约束命题**：长任务性能的主要瓶颈何时来自 Harness 而不是模型？
2. **状态分离命题**：会话、Harness、沙箱三层怎样分离才能兼顾恢复与安全？
3. **最小复杂度命题**：什么证据足以证明图编排、多 Agent 或长期记忆值得其成本？
4. **结果评测命题**：如何让环境终态成为裁判，并用轨迹只做诊断？
5. **现场复利命题**：如何把一次客户特例变成配置、组件、评测和产品能力，而不是永久分叉？

这五个命题会与 FDE 路线合流：Harness 的最高目标不是让模型“看起来更聪明”，而是让客户在真实约束下得到可测量、可接管、可恢复的结果。
